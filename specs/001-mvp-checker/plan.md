# План реалізації 001: прототип перевірки оформлення

Технічна відповідь на [spec.md](spec.md). Технічні рішення приймаються тут; специфікація каже лише «що» і «навіщо».

## Стек

| Частина | Вибір | Чому |
| --- | --- | --- |
| Мова | Python 3.12 | Найкраща бібліотека для .docx, усі в команді знають |
| Читання й запис .docx | `python-docx` + `lxml` для прямого доступу до OpenXML | `python-docx` не бачить усього (успадкування стилів, поля колонтитулів) |
| Правила | YAML + `pydantic` для валідації | Методичка — це дані (принцип 5) |
| CLI | `typer` | Простий CLI з підказками |
| Веб-демо | `streamlit` | Демо за один вечір; деплой на Streamlit Community Cloud безкоштовно |
| Тести | `pytest`; фікстури генеруються скриптом через `python-docx` | Принцип 8 |
| Якість коду | `ruff`, GitHub Actions: lint + тести на кожен PR | Щоб п'ятеро людей не ламали одне одному код |
| Репозиторій | GitHub, **приватний** | Код і реальні роботи для тестів не мають бути публічними |
| Дизайн і мокапи | Figma | Єдине місце для макетів інтерфейсу, лендингу й візуалів демо |

Інструмент розробки для кожної задачі (редактор, ШІ-асистент тощо) не фіксується в плані: перед початком задачі виконавець питає про нього user.

Пізніше, не в MVP: FastAPI + власний фронтенд замість Streamlit.

## Архітектура

```
.docx ──► loader ──► DocumentModel ──► RuleEngine ──► Report ──► JSON / HTML
                         │                  │
                         │                  └─ rules: R01…R10 (кожне — окремий клас)
                         └──────────► Fixer ──► нова копія .docx
```

- **loader** — відкриває файл, перевіряє розмір і формат (FR-001), будує `DocumentModel`.
- **DocumentModel** — обгортка над `python-docx`, яка повертає **ефективні** значення: шрифт, розмір та інтервал з урахуванням ланцюжка «run → стиль абзацу → базовий стиль → docDefaults → тема». Це найризикованіша частина: `python-docx` повертає `None`, коли значення успадковане.
- **RuleEngine** — бере набір правил з YAML, запускає перевірки, збирає `Finding`.
- **Fixer** — для правил з `autofix: true` змінює копію документа, потім повторно перевіряє її (сценарій С2).
- **Report** — `Finding(rule_id, severity, location, actual, expected, quote, fixable)`; рівні: `error`, `warning`, `manual` (FR-010).

## Формат набору правил

Приклад — [rulesets/lpnu-afm-kontrolna-2025.yaml](../../rulesets/lpnu-afm-kontrolna-2025.yaml). Кожне правило має `id`, параметри, рівень, `autofix` і цитату з методички для звіту.

## Технічні нотатки до правил

| Правило | Як перевіряти | Підводні камені |
| --- | --- | --- |
| R01, R02 | `section.page_width/height`, `section.*_margin` для **кожної** секції | Значення в EMU; допуск ±0,5 мм; альбомні сторінки в додатках не помилка |
| R03, R04 | Ефективний шрифт кожного run в абзацах основного тексту | Кирилиця йде у слот `w:hAnsi`, латиниця в `w:ascii` — перевіряти обидва; тема (`minorHAnsi`) розгортається через theme1.xml; підписи, таблиці, заголовки — окремо |
| R05 | `paragraph_format.line_spacing` = 1.5 або `w:spacing w:line="360" w:lineRule="auto"` | Інтервал «Точно 21 пт» візуально схожий, але це не 1,5 |
| R06 | Абзаци, текст яких (без пробілів і крапки) збігається з назвою структурної частини | «Вступ» малими — теж збіг, але з помилкою регістру |
| R07 | Перед заголовком є `w:br w:type="page"` або `pageBreakBefore` у абзаці чи стилі | Розрив секції з нової сторінки теж підходить |
| R08 | Абзац одразу після абзацу з малюнком (`w:drawing`) має відповідати `^Рис\. \d+\.\d+` | Номер розділу визначаємо за останнім заголовком рівня 1 |
| R09 | Абзац перед таблицею відповідає `^Таблиця \d+\.\d+` і вирівняний праворуч | Назва таблиці може йти окремим абзацом |
| R10 | У верхньому колонтитулі є поле `PAGE`, вирівнювання праворуч; для першої сторінки `titlePg` | Поле буває простим (`w:fldSimple`) і складеним (`w:fldChar`) |

## Ризики

| Ризик | Як знижуємо |
| --- | --- |
| Неправильно визначаємо ефективний шрифт → хибні помилки | Окремий модуль і тести на 6 варіантів успадкування; поки не впевнені — рівень `manual` |
| Fixer ламає документ | Після виправлення відкриваємо копію в LibreOffice headless і перевіряємо, що вона читається |
| Реальні роботи «криві» (копіювання з сайтів, змішані стилі) | Тестуємо на 10 справжніх роботах, а не лише на згенерованих |
| П'ятеро людей конфліктують у коді | Кожне правило — окремий файл і окремий PR; CI обов'язковий |
