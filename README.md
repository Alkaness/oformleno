# Оформлено

Прототип перевірки оформлення студентських робіт (.docx) за одним профілем
кафедри ЕОМ НУ «Львівська політехніка» (2026). Знаходить помилки в полях,
шрифтах, інтервалах, заголовках, підписах рисунків і таблиць та виправляє
частину з них автоматично.

Вимоги MVP — методичні вказівки й таблиця стилів кафедри ЕОМ НУ «Львівська
політехніка» (надані редакції 2026 року). Для тестування придатні лабораторні
роботи, до яких застосовні ці вимоги. Вебдемо містить лише профіль ЕОМ;
перевірених профілів інших кафедр у MVP немає. Прототип перевіряє R01–R10
і показує окремий ручний перелік; це не повний автоматичний нормоконтроль.
Нумерацію й деталі розташування уточнено за лабораторним зразком, обраним
user: [джерела, рішення та ручні перевірки](specs/001-mvp-checker/eom-source-review.md).

> Статус: прототип (MVP 0.1) у розробці. Командний проєкт з дисципліни «Технології розробки стартапів», Львівська політехніка.
>
> Репозиторій публічний за рішенням user від 17.11.2026. Працюємо в Codex без повторного вибору інструмента. Дизайн і мокапи — у Figma через локальний MCP, із застосуванням Taste Skill. Деталі — у [принципах проєкту](memory/constitution.md).

## Навіщо

За наданим підсумком опитування (листопад 2026, **24 відповіді**), **67%**
респондентів втрачали бали через оформлення за останній семестр. Недовіру
до точності перевірки зазначили **13 із 24** учасників. Це підстава
перевіряти прототип на реальних роботах за конкретним кафедральним профілем.

Вибірка переважно з IT (**14 із 24**) і другого курсу (**17 із 24**).
Ці результати описують опитаних учасників; вони не доводять потреби всіх
студентів, спеціальностей чи курсів. Для ширших висновків потрібні ще
15–20 відповідей від інших спеціальностей; до цього підсумку їх не включено.

3. За бажанням завантажуєте виправлену копію файлу. Оригінал не змінюється.

## Швидкий старт

Веб-демо: **[oformleno.streamlit.app](https://oformleno.streamlit.app/)**.
Працює в браузері без встановлення програм.
Код: [Alkaness/oformleno на GitHub](https://github.com/Alkaness/oformleno).

Після встановлення середовища за інструкцією нижче:

### Локальне веб-демо

```bash
uv run --no-sync streamlit run app/streamlit_app.py --server.address 127.0.0.1
```

Відкрийте `http://127.0.0.1:8501`. Демо приймає один `.docx` до 20 МБ
за профілем «Кафедра ЕОМ · 2026 / Лабораторна робота». Оберіть файл,
натисніть «Перевірити документ» і перегляньте помилки та ручні пункти.
Якщо є надійні автовиправлення, кнопка «Переглянути виправлену копію»
відкриє повторний звіт і «Завантажити виправлену копію».
Помилки без автовиправлення й ручні пункти залишаються видимими.

Режим «Звичайний текст» типовий у локальному вебдемо: звичайні абзаци
Word (`Normal` або типовий стиль) вважаються основним текстом і перевіряються
за R03–R05 навіть без стилів кафедри. Calibri 12 та одинарний інтервал
дають помилки з можливістю виправлення нової копії. Заголовки, підписи,
таблиці й код зі своїми стилями не стають основним текстом; невідомі
ролі та непідтримуване форматування потребують ручного перегляду.
Якщо документ має власну структуру стилів, оберіть «За стилями документа».
Обраний режим зазначається у звітах до та після виправлення.
Первинний хмарний сценарій наведено у
[звіті розгортання](specs/001-mvp-checker/feedback-deployment-verification.md).
Публікацію виправлень і блока «Перевірте самі» та успішний справжній
сценарій 21.11.2026 зафіксовано у
[звіті T024](specs/001-mvp-checker/feedback-release-verification.md).

Перевірка й підготовка нової копії виконуються в пам'яті одним запитом.
Завантаження передається одноразовою подією й очищується після обробки,
включно з помилками; оригінал на пристрої не змінюється. У сесії
залишаються лише звіти й змінена копія для завантаження. Кнопка
«Очистити результат» прибирає їх і скасовує попереднє посилання на копію.
Студентські файли не записуються на диск і не потрапляють до спільного кешу.

Усі елементи вибору, перевірки й завантаження українською. Невірний
формат, розмір, пошкоджений документ і помилки обробки мають пояснення.
За відсутності автовиправних помилок зайва копія не зберігається.

### Розгортання на Streamlit Community Cloud (T017)

Для повторного розгортання у [Streamlit Community Cloud](https://share.streamlit.io/) підключіть GitHub
і оберіть «Create app»:

| Налаштування | Значення |
| --- | --- |
| Repository | `Alkaness/oformleno` — публічний |
| Branch | `001-mvp-checker` |
| Main file path | `app/streamlit_app.py` |
| Advanced settings → Python version | `3.12` |
| Secrets | Не потрібні |

Кореневий `requirements.txt` встановлює пакет із поточного репозиторію
в редагованому режимі (`-e .`), щоб оновлення коду й ресурсів працювали
після синхронізації гілки без повторного встановлення пакета.
Редагований режим не замінює перезапуск застосунку після зміни джерел.
Після оновлення гілки в Streamlit workspace оберіть меню застосунку
`⋮ → Reboot → Reboot`, потім перевірте справжнє завантаження й отримання копії.
Нові елементи інтерфейсу можуть з'явитися раніше, ніж оновиться імпортований
Python-код. [Перевірка після reboot](specs/001-mvp-checker/feedback-deployment-verification.md)
фіксує цей випадок і успішний повторний сценарій.
Ресурси інтерфейсу й YAML входять до пакета. `requirements-cloud.lock` фіксує
48 залежностей виконання на тих самих версіях, що й перевірений
`requirements-dev.lock`; інструменти тестування не встановлюються.
Цей файл використовується як constraints, без режиму хешів для локального
пакета. Налаштування `.streamlit/config.toml` не обмежує сервер loopback-адресою;
для локального запуску вона задається командою вище.

Після успішного запуску відкрийте Settings → Sharing і зробіть **застосунок**
загальнодоступним для демо. Sharing визначає доступ до застосунку окремо
від видимості репозиторію.
Перевірте посилання без входу в обліковий запис: завантаження синтетичного
DOCX, звіт, отримання виправленої копії та очищення.
[Стан і докази перевірки T017](specs/001-mvp-checker/streamlit-cloud-verification.md).

У хмарному демо файл передається на сервери Streamlit Community Cloud
у США та обробляється в пам'яті застосунку. Застосунок не записує документ
на диск; звіт містить уривки роботи, а виправлена копія залишається в сесії
до очищення. Це не обробка лише на вашому пристрої. Платформа має власні
журнали й аналітику та може перевизначати `gatherUsageStats`; вимкнення
в локальному конфігу не гарантує вимкнення аналітики хостингу.
Деталі: [обмеження Community Cloud](https://docs.streamlit.io/deploy/streamlit-community-cloud/status).
Після 12 годин без відвідувачів демо засинає; перед показом відкрийте його
та дочекайтеся готовності.
[Керування застосунком](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app).

### CLI

```bash
oformleno check work.docx --rules lpnu-eom-styles-2026 --document-type laboratory_report
oformleno check --help
```

`--rules` приймає ідентифікатор вбудованого набору або шлях до власного
YAML-файлу. Типово використовується `lpnu-eom-styles-2026`.
Тип роботи можна вказати як `laboratory_report`, `qualification_thesis`
або `other_printed_work`; без нього застосовність спеціальних вимог
уточнюється вручну. Зокрема, від лабораторної роботи не вимагається
обсяг БКР/МКР у 60–100 сторінок.

Типово команда `check` виводить один звіт JSON у стандартний потік виводу.
Він містить висновки з цитатами, походження уточнень за зразком, список
виконаних, відсутніх і невдалих перевірок та підсумок `summary`:
`errors`, `warnings`, `manual`, `fixable`, `status` й українське пояснення.
Помилки введення повертаються окремим JSON у стандартному потоці помилок,
без тексту або персональної назви роботи.

API й CLI типово визначають основний текст за відомими стилями (`styles`).
Для звичайних абзаців без стилів кафедри передайте `--body-text-mode ordinary`
обом командам, наприклад:

```bash
oformleno check work.docx --document-type laboratory_report --body-text-mode ordinary
oformleno fix work.docx --output new-copy.docx --document-type laboratory_report --body-text-mode ordinary
```

Python API `RuleEngine.check`, `fix_document` і `fix_document_bytes` приймають
`body_text_mode="ordinary"`. JSON містить поле `body_text_mode`; цей режим
визначає роль звичайних абзаців, а параметри й цитати ЕОМ залишаються тими самими.

Для звіту, який можна прочитати у браузері, додайте `--format html`:

```bash
oformleno check work.docx --document-type laboratory_report --format html
```

HTML містить підсумок, висновки за правилами, місця порушень, фактичні й потрібні
значення, дослівні цитати та окреме походження уточнень за зразком. Ручні
висновки й застосовні пункти M01–M08 зібрано в один початково згорнутий
блок «Перевірте самі» після помилок. Його можна розгорнути за правилами;
усі причини, місця й цитати збережено. JSON містить усі окремі висновки.
Нуль автоматичних помилок не означає завершеного нормоконтролю. Коди завершення
та JSON-помилки у stderr однакові для обох форматів.

Це самодостатній HTML з вбудованими стилями: без скриптів і зовнішніх запитів.
Вміст звіту екранується як текст. Функція повертає рядок, не записує файлів
і не логує уривки; звіт містить уривки роботи, тому зберігайте його приватно.
Рендерер [report_html.py](src/oformleno/report_html.py) також доступний із Python:

```python
from oformleno.engine import RuleEngine
from oformleno.loader import load_document
from oformleno.report_html import render_report_html
from oformleno.ruleset import load_ruleset

report = RuleEngine().check(
    load_document("work.docx"), load_ruleset(), document_type="laboratory_report"
)
html_text = render_report_html(report)
```

| Код завершення | Значення |
| --- | --- |
| `0` | Перевірки виконано без помилок і ручних висновків; можливі попередження |
| `1` | Знайдено помилки оформлення |
| `2` | Помилка файла, набору правил або аргументів команди |
| `3` | Потрібна ручна перевірка або автоматичні перевірки ще недоступні |

Реалізовані перевірки R01–R10. R01 (розмір сторінки) і R02 (поля) працюють для кожної секції, з
параметрами та допуском із YAML. R01 враховує орієнтацію: для альбомної
сторінки очікувані ширина й висота міняються місцями. R02 показує кожне
порушене поле окремо; наприклад, ліве поле 20 мм замість 25 мм.
Висновок містить номер секції, фактичні й потрібні значення в міліметрах,
пояснення та цитату. Порівняння використовує повну точність, без округлення
до вигляду в повідомленні.

Відсутні, неоднозначні або непідтримувані властивості дають `manual`.
Зокрема, R02 потребує ручної перевірки для дзеркальних полів,
книжкового макета чи додаткового відступу для переплетення.
R03–R05 перевіряють ефективні шрифт, розмір та інтервал лише підтвердженого
основного тексту. Відомі ролі визначаються за стилями й структурою;
таблиці, підписи, заголовки, програмний код та колонтитули не перевіряються як основний
текст. «ЕОМ: Основний» і вбудований `Body Text`, а також їхні похідні стилі
розпізнаються без оцінки шрифту чи розміру. Інші ролі потребують `manual`.
Для власного набору можна явно задати `body_styles` у параметрах R03–R05.
«ЕОМ: Програма» та її похідні зберігають роль коду, навіть успадковуючи
типографіку основного тексту; суперечливий явний body_styles дає `manual`.
Висновки містять номер абзацу від 1 серед абзаців основної частини документа
поза таблицями, включно з порожніми абзацами й заголовками, та уривок до
50 символів. Перевіряються використані шрифтові набори, успадковані розміри
та кратність інтервалу; точно або щонайменше 21 пт не замінюють 1,5 рядка.
Невідоме успадкування залишається ручною перевіркою; підтверджена помилка
й окрема невизначеність можуть бути показані для одного абзацу.

R06 перевіряє форматування впевнено розпізнаних структурних заголовків:
назва з переліку YAML та відомий стиль заголовка або структурний рівень;
або структурний стиль із параметрів правила та його похідні, навіть якщо
назва відсутня в переліку. Це охоплює заголовки переліку таблиць і
бібліографії. Довільний вбудований заголовок без відомої назви не дає
підстав застосовувати R06.
Перевіряються вирівнювання, великі літери, напівжирний, шрифт, розмір та
інтервал з урахуванням успадкування. Великі літери визначаються властивістю
Word `caps`, включно зі стилем, а не лише регістром тексту. Стиль не
перейменовується; текст, кінцева крапка й розрив сторінки не змінюються.
Невідомі/суперечливі ролі, назви з результатів полів, зміни стилів та неоднозначні перемикачі
залишаються ручними. Наявність усіх перелічених структурних частин не
вимагається; обов'язкові стилі окремо перевіряються за M01.

Літеральний заголовок перед початком блочного поля змісту або після
його закриття перевіряється окремо від поля. Межі враховуються через
абзаци; кешований заголовок і непевні поля залишаються ручними.

R07 перевіряє заданий початок структурних заголовків з нової сторінки:
успадкований `pageBreakBefore`, явний розрив `w:br` або посторінковий
розрив секції. Природне розбиття тексту на сторінки не обчислюється;
непевні межі, поля, прихований вміст і непосторінкові секції дають `manual`.

R10 перевіряє поле `PAGE` у вибраних верхніх колонтитулах: праворуч,
Times New Roman 12 пт. Враховуються звичайні, парні та перші колонтитули,
їх незалежне успадкування, `titlePg` і режим парних/непарних сторінок.
Порожнім має бути колонтитул першої сторінки документа; перші сторінки
наступних секцій не звільняються від нумерації. Перевіряються інструкції
простих і складених полів та успадковане форматування, без довіри до
кешованого номера сторінки. Складні поля, таблиці/об'єкти в колонтитулах,
табуляції, невизначена геометрія та потенційно невикористані порожні
варіанти потребують ручної перевірки. Читання не створює частин колонтитулів.
Автовиправлення R07/R10 не підтримується.

R08 перевіряє підпис під рядковим рисунком: вирівнювання, шрифт, 12 пт,
курсив і полуторний інтервал. R09 перевіряє суміщений номер і назву над
таблицею: шрифт, 14 пт, напівжирний курсив, центрування, полуторний
інтервал і властивість «Не відривати від наступного». Обидва правила
читають успадковане форматування, прості та складені поля `STYLEREF`/`SEQ`,
роздільник і окремі лічильники з перезапуском на рівні розділу з YAML.
Перевіряється задана схема нумерації, без оновлення полів або довіри до
кешованих чисел. Невідомі ролі, нестандартні розділи, нерозібрані поля,
плаваючі об'єкти, непевні зв'язки й альтернативний макет таблиці дають
`manual`. Сторінкове компонування не обчислюється; невиявлений підпис
об'єкта потребує ручного уточнення його ролі. Автовиправлення R08/R09 немає.

Застосовний перелік M01–M08 залишається ручним. Для коректного згенерованого
лабораторного прикладу наразі є 7 ручних висновків, без указаного типу — 8.
Невизначені ролі чи властивості додають окремі ручні висновки. Команда повертає `1`
за наявності помилок або `3`, якщо помилок немає, але перевірка неповна.
Цей звіт не означає, що робота пройшла повний нормоконтроль.
Надійно визначені порушення R01–R06, для яких YAML дозволяє автовиправлення
і потрібне значення можна зберегти з точністю DOCX, мають `fixable: true`.
Ручні висновки не виправляються.

### Виправлена копія

```bash
oformleno fix work.docx --output corrected.docx --rules lpnu-eom-styles-2026 --document-type laboratory_report
oformleno fix --help
```

Команда створює новий файл і відмовляється перезаписувати оригінал або
будь-який наявний файл призначення. Виправляються лише підтверджені R01–R06
з `autofix: true`. Форматування основного тексту змінюється локально,
без зміни спільних стилів, підписів, комірок таблиць або колонтитулів.
Для R06 змінюється лише підтверджене локальне форматування заголовка;
текст, пунктуація, стиль і початок нової сторінки зберігаються.
Вміст, рисунки, поля та структура зберігаються; невизначені елементи
залишаються для ручної перевірки.

Перед записом копія повторно відкривається й перевіряється. Якщо перевірка
збереження вмісту або виправлень не проходить, файл не створюється.
JSON у stdout містить `before`, `after` та `applied_rules`. Код завершення
відповідає звіту `after`: зокрема, `3` означає, що копію створено, але
залишаються ручні перевірки; `1` — залишилися помилки, які не виправлялися.
Код `2` означає помилку введення, виправлення або запису. Оригінал не змінюється.

Ті самі операції доступні з Python:

```python
from oformleno.fixer import fix_document, fix_document_bytes
from oformleno.ruleset import load_ruleset

ruleset = load_ruleset()
result = fix_document("work.docx", "corrected.docx", ruleset)
uploaded_result = fix_document_bytes(uploaded_bytes, ruleset, filename="work.docx")
corrected_bytes = uploaded_result.document_bytes
```

`FixResult` містить `document_bytes`, звіти `before`/`after` і `applied_rules`.
Варіант для байтів працює в пам'яті без тимчасових файлів; файловий варіант
перевіряє результат до створення нового файла з приватними дозволами.

### Завантаження з Python

Модуль [loader.py](src/oformleno/loader.py) відкриває `.docx` з диска
або з даних у пам'яті. Ліміт — 20 × 1024 × 1024 байтів включно;
розширення `.DOCX` також дозволене. Пошкоджені документи й інші формати
відхиляються з українським поясненням через `DocumentLoadError`.

```python
from oformleno.loader import load_document, load_document_bytes

document = load_document("work.docx")
uploaded_document = load_document_bytes(uploaded_bytes, filename="work.docx")
```

Завантажувач повертає документ `python-docx` у пам'яті, не змінює оригінал
і не створює тимчасових копій. CLI використовує цей самий завантажувач.

### Ефективне форматування з Python

[DocumentModel](src/oformleno/model.py) розгортає успадковані назви шрифтів,
розміри в пунктах і міжрядковий інтервал. Враховує пряме форматування,
символьні й абзацні стилі, їхні базові стилі, `docDefaults` і посилання на тему.

```python
from oformleno.model import DocumentModel

model = DocumentModel(load_document("work.docx"))
paragraph = model.paragraphs[0]
formatting = model.run_formatting(model.runs(paragraph)[0])
spacing = model.effective_line_spacing(paragraph)
```

Результат `Resolution` містить `value` і джерело `source` або українську
причину `reason` для ручної перевірки. `formatting.fonts` розділяє набори
`ascii` та `hAnsi`; `formatting.size_pt` повертає пункти. Інтервал має тип
`multiple`, `exact` або `at_least`: 1,5 рядка й точно 21 пт — різні значення.
Відсутній шрифт не замінюється здогадкою про типовий шрифт Word.

`model.paragraphs` охоплює основний текст, включно з елементами керування
вмістом; таблиці доступні окремо через `model.tables`. `model.runs()` також
бачить фрагменти гіперпосилань і полів. Модель не визначає роль основного
тексту й не перевіряє правила самостійно. Непідтримуваний контекст, зокрема
успадкування від таблиці чи нумерації, невизначений символьний набір або
колонтитул, потребує ручної перевірки. [Контракт і межі](specs/001-mvp-checker/plan.md#ефективне-форматування-t006).
Після редагування документа створюйте нову модель; її запити не змінюють XML
і не додають відсутні частини пакета.

## Середовище розробки

Потрібні Python 3.12 і [uv](https://docs.astral.sh/uv/getting-started/installation/).
Встановлення залежностей і спільна перевірка для розробника та CI:

```bash
uv venv
uv pip sync --require-hashes requirements-dev.lock
uv pip install --no-deps --no-build-isolation -e .
sh scripts/check.sh
```

`requirements-dev.lock` фіксує версії та хеші залежностей для Python 3.12
і Linux x86_64 (поточне середовище та CI). `scripts/check.sh` запускає Ruff,
перевірку форматування та pytest. Тести створюють синтетичні `.docx`
у тимчасовій теці; роботи в репозиторій не додаються.

Пакет має структуру `src/oformleno`. T005 додала Pydantic, PyYAML і Typer;
T016 додала Streamlit 1.67 разом із зафіксованими залежностями та ресурсами UI.
Окремі перевірки веб-обробки й подій застосунку:

```bash
uv run --no-sync pytest tests/test_web.py tests/test_streamlit_app.py
```

Генератор `scripts/verify_web_frontend.py` створює тимчасову HTML-перевірку
справжнього браузерного компонента на згенерованих DOCX. Вона перевіряє
FileReader, валідацію, байти Blob для завантаження й очищення; AppTest
окремо перевіряє справжні події та стан Streamlit. Реальні роботи не потрібні.

Оновлення lock-файлу після зміни `pyproject.toml`:

```bash
uv pip compile pyproject.toml --group dev --python-platform x86_64-unknown-linux-gnu --python-version 3.12 --generate-hashes -o requirements-dev.lock
uv pip compile pyproject.toml --constraint requirements-dev.lock --python-platform x86_64-unknown-linux-gnu --python-version 3.12 --output-file requirements-cloud.lock
```

Для іншої ОС залежності потрібно розв'язати для її платформи; наведений
lock-файл перевірено лише для Linux x86_64.

### Синтетичні приклади DOCX (T007)

Після встановлення середовища згенеруйте приклади у новій тимчасовій теці:

```bash
uv run --no-sync python tests/fixtures/make_fixtures.py
```

Команда повідомить шлях до створеної теки. Можна передати власну нову
тимчасову теку аргументом; наявні файли прикладів не перезаписуються.
Генератор створює 20 документів без використання студентських робіт:
`good.docx`, `bad_r01.docx`–`bad_r10.docx` і дев'ять додаткових прикладів.
Вони охоплюють успадковані та явні розриви сторінок, секції з успадкуванням
колонтитулів, прості й складені поля Word, окремі лічильники рисунків
і таблиць у двох розділах, шрифтові набори, точний інтервал та випадки `manual`.
Коректні комірки таблиць і підписи рисунків мають 12 пт.

`manifest.json` містить опис і очікувані `error_rules`/`manual_rules` кожного
прикладу для R01–R10. Це задані очікування для майбутніх тестів правил,
а не результат перевірки. Застосовні M01–M08 залишаються ручними, навіть
для `good.docx`; перевірки R01–R10 реалізовано в T008–T013.
Виправлення підтримує лише R01–R06.
Тести отримують шляхи через фікстуру pytest `eom_fixtures`; усі документи
створюються в тимчасовій теці. До Git додається лише код генератора й тестів.

## Оцінювання на реальних роботах (T014)

Повнота R01–R06 на цій вибірці — 100% за XML-оглядом і підтвердженням user.
Ці роботи використовувалися для виправлення дефектів: результат T014
стосується розробницької вибірки й не є незалежною оцінкою точності.
T014 завершена; інші ручні пункти не означають повного нормоконтролю.
Приватні артефакти та робочі копії зберігаються поза Git.

На п'яти нових роботах [незалежної перевірки T021](specs/001-mvp-checker/holdout-validation.md)
незмінний перевіряч має **112/112 підтверджених автоматичних помилок**,
але знаходить лише **23/38 порушень R01–R06: повнота 60,53%**, нижча за
ціль 80%. Еталон зі сліпого XML-аудиту зафіксовано до першого запуску;
він не є суцільною людською експертною атестацією. Пропущено 5 порушень
шрифту з ручним статусом і 10 структурних заголовків поза буквальним
переліком назв. Вибірка одного профілю зі спільним шаблоном не доводить
точності для всіх студентів або документів без кафедральних стилів.

Після [виправлення цих пропусків T021a](specs/001-mvp-checker/holdout-regression.md)
повторний прогін знаходить усі 38/38 відомих порушень R01–R06; п'ять
виправлених копій не містять автоматичних помилок R01–R06, ручні
перевірки залишаються. Це регресія на вже використаних даних, окремо
від первинного незалежного результату 60,53%.
